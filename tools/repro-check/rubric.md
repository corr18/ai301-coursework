# Rubric: is this reproduction package ready to post?

Read the whole package against the issue before grading. Every check
judges the outcome (what the artifacts and words actually show against
what the issue describes), never the write-up's length, polish, or
headings. A terse report can pass every check; a long confident one can
fail all of them. Locations named below are defined in
`references/evidence-guide.md`.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| environment-recorded | The repro report's environment record (the line or block naming versions, OS/platform, install method, and any issue-relevant setting), read against the issue's stated environment and the repo-facts block's bug-report template asks | The report names the tool's version and the platform it ran on, plus any setting the issue or thread says changes the failure (driver, shell, build profile, locale, backend). Where the attempt's version or platform differs from the issue's, the report says so explicitly ("filed against X; tested on Y"). Fail if there is no environment record, if a setting the issue depends on is missing, or if the version/platform silently differs from what the issue targets (for example, an old release tested against a bug confirmed on latest/main with no mention of the gap). | required |
| steps-rerunnable | The repro report's steps and commands, plus any input files or configs they use, read from a clean starting state through to the trigger the issue names | A stranger with only the public project and the report could re-run the attempt: every input is shown inline, is public, or is described precisely enough to recreate it (for example, "a minimal env.yml with a valid `dependencies:` list plus a `category:` section" names the property that triggers the bug), every command or UI action that matters is stated, and the steps include the actual trigger the issue describes. Fail if the attempt depends on private code, an unshared config, or an unstated setup step, or if there are no steps at all. Brevity is fine; completeness is what counts. | required |
| behavior-matches-issue | The repro report's artifacts (output excerpts, logs, exit codes, file contents) read against the issue body's described symptom, error message, and trigger, and against owner notes in the thread highlights | The shown artifact is the issue's behavior, produced by the issue's trigger: same error/symptom class, same kind of failure (a crash is a crash, a panic is a panic, wrong output is wrong output), same input shape. A cannot-reproduce passes here when it is a genuine attempt at the issue's trigger with its output shown, even if the report itself admits its setup may not have reached the triggering condition; whether that admission is honest is `outcome-honest`'s job, not this check's. This allowance covers only reports that say they did NOT reproduce; a report that claims to reproduce must show the issue's own behavior. Fail if there is no artifact, if the artifact shows only that the program runs, or if it shows an adjacent behavior (a different error, a graceful validation message instead of the reported crash, a compile error from a modified input, garbled output presented as a crash). | required |
| outcome-honest | The repro report's stated outcome ("reproduced", "cannot reproduce", "expected/actual") and the claim comment's statements about the repro, each read against the artifacts that back them | Every claim that decides the outcome is supported by an artifact in the package (a plain side observation stated in prose, such as "without `-r` the output is correct", is not an overclaim and does not need its own artifact): "reproduced" only when the artifact shows the issue's behavior, a root cause only when shown evidence supports it, a scope ("also affects X") only when X was tested. An evidenced cannot-reproduce passes: it shows the attempt, states it did not reproduce, and names what differed or what is likely needed. Fail on certainty narrated over missing or mismatched evidence ("guaranteed reproducible", "I verified the race", "confirmed on two machines" with no artifact that shows it), or on expected/actual statements that contradict the artifacts. | required |
| claim-specific-and-modest | The claim comment, read against the issue's title and body | The claim names something specific to this issue (its symptom, trigger, component, or the reporter's environment) so it could not be pasted unchanged onto another issue, and states a concrete next step the commenter will take. It promises only investigation or a next step, never a guaranteed fix, a deadline, or a demand to reserve/assign the issue. Fail on a bare "+1"/"me too", interchangeable "please assign me" boilerplate, or any promised fix or date. | required |
| repo-conventions | The repo-facts block's contribution policy (CONTRIBUTING / AI_POLICY wording) and bug-report template asks, read against the text of the claim comment and repro report. Treat every eval package as AI-assisted work. | If the repo's stated policy requires disclosing AI use (in any form, including "must disclose", "state the tool used"), at least one of the two comments contains an explicit AI-use disclosure; missing disclosure fails this check no matter how good the repro is. If the policy only requires that comments be written by a human in their own words, pass when the comments read as first-person, specific, and self-authored. If the policy is permissive or silent on AI, this check passes. Missing bug-template fields are judged by `environment-recorded`, not here. | required |
| control-run | The repro report's artifacts | The report shows a control or contrast run (the same steps with the trigger removed or swapped) that isolates the behavior. Nice to have; its absence never holds a package. | preferred |

## Verdict rule

Accept if every `required` check passes. Reject if any `required` check
fails. `preferred` checks never change the verdict. `unclear` on a
required check counts as fail, except in live mode's claim-only state,
where checks marked `not yet applicable: claim-only draft` are left out
of the verdict entirely (on a claim-only draft, only
`claim-specific-and-modest` and `repo-conventions` decide it).
