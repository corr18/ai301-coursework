# Rubric: is this plan ready to post and build from?

Every check below judges the plan or comment itself (is the cause right, is
the change one change, could a stranger start, would the test prove the fix,
does the comment answer the thread and the repo's rules), never how the write-up
is formatted. A terse plan with no headings can pass every check, and a long,
polished one can fail them.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| cause-fits-evidence | The plan's stated cause (its diagnosis: the component, code path, or mechanism it blames), read against every step, control run, and artifact in the repro-evidence block (see evidence guide, "Diagnosis and grounding") | Pass if the blamed cause explains what the repro evidence shows AND no step or control in the repro evidence rules it out. A control rules a cause out when the symptom shows up with the blamed component absent or bypassed, when the blamed component is shown working correctly in the same build, or when an intermediate artifact shows the damage already done before the blamed stage runs. Fail if any control contradicts the cause, even if the issue author, the thread, or the plan states that cause confidently; a confident thread diagnosis does not overrule the package's own evidence. Fail if the plan names no cause at all. | required |
| one-bounded-change | The plan's change, in-scope and not-in-scope statements, and approach steps, read against the issue's reported behavior (evidence guide, "Scope") | Pass if every piece of work the plan commits to is needed to fix the reported behavior or to test that fix. Fixing the same bug pattern at a sibling site the repro or issue points at, adding regression tests, a doc line for the changed behavior, and "look and report in the PR without fixing" audits all count as needed. Explicit deferrals ("not in scope: X, because Y") are a strength, not a gap. Fail if the plan also commits to work the issue's behavior does not require: dependency upgrades or library migrations, refactors or rewrites of surrounding code, new options or settings, UI changes, CI or test-harness changes, or "while I'm in here" fixes, even when the core fix inside the bundle is right. | required |
| stranger-can-start | The plan's approach, files or areas named, and order of work (evidence guide, "Executability") | Pass if someone who has never talked to the author could start building today: the plan picks ONE mechanism for the fix (not "A or B, whichever is easier", not "investigate X"), AND names where it goes (a file, module, or component specific enough to open). Exact function names may be left to the build when the area is named and the plan states a concrete way it will pin them (for example a named debug trace). Fail if the plan's main move is to investigate, profile, or "poke around"; if it leaves the layer or location open ("somewhere", "not sure which"); or if the core decision is deferred to build time. | required |
| test-proves-fix | The plan's test plan, read against the repro evidence's steps, expected result, and artifact (evidence guide, "Test plan") | Pass if the test plan names at least one observable outcome that would differ between the broken and fixed code: the repro steps re-run with a stated expected result (an exit code, an output, a behavior that now happens), or a named regression test asserting the issue's specific case. Fail if the only test is that the existing suite still passes / nothing regresses, if the outcome is a feeling ("should feel fast", "nothing should feel broken"), or if no test plan is given. | required |
| thread-direction-engaged | The plan comment (and the plan), read against the thread highlights for comments by maintainers, owners, members, or collaborators (evidence guide, "Comms") | Pass if the thread has no maintainer direction, OR the comment engages every piece of direction present: it follows it, or names it and says why it departs. Direction means a maintainer naming the culprit code, proposing or rejecting an approach, posting a patch or test binary and asking for testing, or pointing at an open or prior PR for the same fix. Engaging a prior PR means saying how this work relates to it (building on it, rebasing onto it, or deferring to it). Fail if the comment proceeds as if that direction were not in the thread, for example proposing a different kind of fix without mentioning the maintainer's culprit or patch. | required |
| ai-disclosure | The repo-facts block's contribution policy (AI policy line), read against the plan comment's text (evidence guide, "Comms") | Treat every package as AI-assisted work. Pass if the repo states no AI policy, or its policy asks for disclosure only in the pull request (not in issue comments), or the policy asks only that comments be in the contributor's own words. Fail if the policy requires disclosing AI use in comments or "in any form", and the comment has no sentence stating that AI was used, which tool, and how much. | required |
| unknowns-stated | The plan's risk, unknowns, or open-question lines, read against what the repro evidence does not cover (evidence guide, "Honesty") | Pass if the plan names at least one thing it has not verified (a risk, an untested platform, a cost not yet measured, a site it will check) or the change is small enough that no real unknown exists. Fail if the plan claims certainty about things the evidence does not show (for example "this cannot affect anything else" with no check behind it). | preferred |

## Verdict rule

Accept only if all six required checks grade `pass`. Any required check
graded `fail` or `unclear` means reject: `unclear` counts as fail, because a
plan a grader cannot confirm is a plan a maintainer cannot confirm either.
`unknowns-stated` is preferred: report it, but it never changes the verdict.
The deciding check quoted in the summary is the first required check, in
table order, that did not pass.
